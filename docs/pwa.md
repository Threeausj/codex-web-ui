# PWA 与后台通知

**简体中文** · [English](pwa.en.md)

Codex Web UI 可以安装到手机主屏幕，并在用户主动授权后使用标准 Web Push。通知由仍在运行的 Node 服务根据 app-server 事件发送；网页无需保持打开。回复完成、需要审批或补充输入、运行失败都可以独立选择。Web Push 能在页面未加载时唤起 Service Worker，这是浏览器提供的能力。[MDN Push API](https://developer.mozilla.org/en-US/docs/Web/API/Push_API)。

## 部署准备

- 使用设备可访问的公网 HTTPS 域名和受信任证书，`PUBLIC_ORIGIN` 与访问地址完全一致。Docker 用户按 [公网部署](docker.md#公网-https) 使用 Caddy overlay。
- 使用生产构建：Node 部署执行 `npm run build` 后 `npm start`；Docker 镜像已包含该构建。Vite 开发模式不注册 Service Worker，不能用于安装/后台推送验收。
- Node 服务、对应 app-server 和任务保持运行，服务器能够访问浏览器厂商的推送服务。支持官方 FCM、Mozilla、Apple 和 Windows 推送地址；后端拒绝任意自定义 endpoint，不提供放宽域名校验的环境变量。
- 持久化 `DATA_DIR`。Docker 的 `webdata` 卷已经包含推送密钥和设备授权；安装 PWA 无须 Apple 开发者账户或另外部署通知中转服务。
- 每台设备分别登录、安装和启用通知。安装应用不自动授予通知权限，系统或浏览器拒绝后需到其设置中重新允许。

通知许可由用户点击“启用通知”触发；支持的浏览器要求安全上下文，不能用普通公网 HTTP 代替 HTTPS。[MDN 通知许可](https://developer.mozilla.org/en-US/docs/Web/API/Notification/requestPermission_static)。本机 loopback 仅供开发调试，手机通过局域网 HTTP 访问不属于这套公网验收方案。

## Android / Chrome

1. 用 Chrome 打开部署的 HTTPS 地址并登录。
2. 进入“设置 → 应用与通知”，有安装提示时点击“安装应用”；也可使用浏览器菜单中的安装选项。已经安装或浏览器未提供安装提示时，不重复弹出安装框。
3. 打开安装后的应用，在同一设置页面点击“启用通知”，允许系统许可；选择所需类别。
4. 点击“发送测试通知”，确认系统通知可见。浏览器名称、系统通知入口和安装菜单会随版本变化，以设备实际显示为准。[MDN PWA 安装](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Installing)。

测试按钮会显示发送进度、失败原因或“推送服务已接收”。接收成功表示厂商接受请求，手机送达仍需核对通知栏。“检查系统通知”直接通过当前设备的 Service Worker 显示通知，可以单独检查应用的系统通知权限和显示渠道；它不验证后台推送网络。若系统检查正常、远程测试却没有送达，检查手机连接 Google 推送服务的网络及省电限制。FCM 的设备连接需要允许 TCP 443、5228–5230 和相应 Google 主机，普通 HTTP 代理不代理该连接。[Firebase 网络说明](https://firebase.google.com/docs/cloud-messaging/network-configuration?hl=zh-cn)。

测试通知使用独立的通知标识，避免重复测试互相覆盖；任务通知以高优先级发送，同一对话的新提醒替换旧提醒时重新提示。

## iPhone / iPad

1. 使用 iOS/iPadOS **16.4 或更新版本**，在 Safari 打开部署的 HTTPS 地址。
2. 点击“分享 → 添加到主屏幕”，确认添加。
3. 从主屏幕图标打开 Codex Web UI，再完成网页登录。普通 Safari 标签页中的登录与主屏幕应用状态需要在实际设备核对。
4. 在“设置 → 应用与通知”主动点击“启用通知”，再允许系统提示；仅添加图标不会自动请求权限。
5. 点击“发送测试通知”，到系统通知设置核对该应用的提醒方式；专注模式可能使提醒静默。

iOS/iPadOS 的这项 Web Push 能力用于主屏幕 Web 应用，许可请求必须由用户交互触发，支持锁屏和通知中心，并遵循系统专注设置。[WebKit 官方说明](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)。

## 类别、隐私与授权期限

“回复已完成”“需要审批”“运行出错”默认全部开启；审批类别也包含等待补充输入的请求。类别是每台设备的选择，其他设备可以独立设置。“关闭通知”取消当前设备订阅，不修改其他设备。

任务通知的标题显示对话名，正文显示事件，例如标题“部署项目”、正文“运行完成”“运行失败”“等待命令执行确认”或“等待补充输入”。对话名与网页列表一致：优先使用已设置的名称，其次使用预览标题，都不可用时使用“未命名对话”。通知不附带回复正文、文件路径或命令；对话名会显示在系统通知中。导航数据只用于打开对应主机和对话；点击通知后仍需网页登录，通知不会批准请求或执行操作。

设备授权最长 **30 天**，浏览器订阅自身若提前过期则取更早时间，与 **30 天网页登录会话**分别管理。网页自然过期或 Node 服务重启不会直接撤销仍有效的设备授权；登录后恢复并保存已有订阅可续期。明确退出登录会撤销该登录关联的设备订阅，其他设备不受影响。在“设置 → 账户 → 网页访问”修改访问密码则撤销其他设备的登录和后台通知授权，当前登录关联的设备保留。清理浏览器数据、撤销系统权限、删除持久化数据或轮换 VAPID 密钥后，应重新登录并启用通知；推送服务返回 404/410 时后端删除失效订阅。

密钥与订阅文件位于 `DATA_DIR`，权限为 `0600`：

| 配置/文件 | 用途 |
| --- | --- |
| `push-vapid.json` | 未手动配置时自动生成的 VAPID 密钥对 |
| `push-subscriptions.json` | 设备 endpoint、订阅密钥、授权期限及类别 |
| `PUSH_VAPID_PUBLIC_KEY` / `PUSH_VAPID_PRIVATE_KEY` | 可选的既有密钥对，必须成对设置；全部留空则自动生成 |
| `PUSH_SUBJECT` | 可选 VAPID 联系地址，建议 `mailto:维护者真实邮箱`；默认取第一个 HTTPS `PUBLIC_ORIGIN`，本机 HTTP 环境回退到项目 GitHub URL |

把这些文件与私有环境配置一起备份，不提交到仓库。保留 VAPID 密钥和订阅可以避免常规重建后重新授权；更换域名或密钥后重新注册设备。无需手工生成密钥才能开始部署。

## 运行边界与更新

应用恢复可见、从冻结状态恢复、从页面缓存返回或网络恢复时，会自动检查登录和连接。仍显示 OPEN 的旧连接通过限时只读请求检测；无响应则重新连接，并从服务器同步当前对话。主机、项目、已选对话和草稿通过浏览器本地存储保留，重进后自动恢复；既有通知订阅也会重新同步并续期。恢复连接不会自动重发消息、命令或审批。

私有 API 的读取会附加每次请求唯一的缓存参数，并使用 `no-store`，避免上游误缓存的“未登录”结果使应用返回登录页。测试通知请求返回 401 或 WebSocket 因认证关闭时，应用先重新核对当前 Cookie 对应的会话；只有新的会话查询确认失效才退出登录，临时网络错误或旧登录的延迟响应不会清除当前登录。

Android 可以冻结或回收后台页面，因此不能靠一直保留浏览器 WebSocket 实现持久运行。实际任务由服务器的 app-server 继续执行，手机返回后恢复连接并读取任务状态。[Chrome 页面生命周期](https://developer.chrome.com/docs/web-platform/page-lifecycle-api)。

关闭页面、应用进入后台或锁屏后，后端仍会接收已经连接的主机事件并尝试推送；启动时有有效订阅会尝试恢复已配置主机连接。通知不会让已停止的 Node 服务或 Codex 任务继续执行。重启容器会结束容器内活动进程；磁盘持久化无法恢复其执行状态，proxy/远端存活任务的通知取决于 app-server 的重连事件。

送达依赖浏览器厂商服务、网络、设备通知权限、专注模式和系统资源策略。关闭页面后的后台推送属于支持范围，系统强退、强制停止、严格省电或系统限制下的即时送达无法保证；也不把通知当作任务结果的唯一记录。回到网页时以 app-server 的真实状态和历史为准。

Service Worker 只缓存公开的应用界面和静态资源，不缓存 API、上传、预览或私人对话。另有按有效登录隔离的 IndexedDB 会话快照，最多保存 12 个会话、总计 4 MiB、24 小时；登出或登录失效时清理。重进优先显示上次会话及缓存历史，随后核对原生会话；同步完成前禁止发送。离线不显示未经登录验证的私人缓存，也不支持发送、审批、文件操作或执行任务。

切到后台时保存最近历史快照，回到前台会检查登录和连接并恢复选中对话。Android 可以冻结或回收 PWA 的页面进程，网页无法强制永久驻留；会话恢复与服务端保留的运行连接用于应对回收。[Chrome 页面生命周期](https://developer.chrome.com/docs/web-platform/page-lifecycle-api)。主动在“资源管理”关闭 Web Codex 后保持暂停，自动重连和服务重启不会抢回桌面端的会话，需显式点击“连接 Web Codex”。

发现新版本后，设置中显示“有新版本可用”。点击“更新应用”才启用更新并重新加载；当前任务运行时按钮禁用，等待任务结束。页面不会因为检测到版本变化而自动刷新。部署升级还需要按照 [Docker 维护说明](docker.md#日常维护与备份) 保留数据并安排服务重启。

反向代理/CDN 应遵循源站缓存头：首页及 manifest 需要重新验证，`sw.js` 与 API 不缓存，仅内容哈希命名的静态资源长期缓存。应用使用带构建版本的 Worker URL，并在 Worker 获取首页和安装资源时附加版本参数。若升级前首页已被上游缓存，先清理域名的 `/`、`/index.html`、`/sw.js` 缓存，或首次通过 `/?update=当前版本` 打开；新 Worker 接管后的导航会主动绕过旧首页缓存。

升级前缺少凭证代际的旧版设备订阅会被撤销，升级后请在各设备重新启用通知。

## 真机验收

以下步骤需要部署者在真实 Android/iOS 设备执行，浏览器模拟与自动测试不等同于真机送达验收。本项目没有宣称已通过真实手机、锁屏或公网推送服务验收。

1. 记录设备、OS、浏览器版本和 HTTPS 域名；Android 和 iOS 分别按上述流程安装，登录并启用通知。
2. 主动发送测试通知，确认通知中心/锁屏显示通用文案；检查系统通知权限与专注、省电设置。
3. 在已登录的另一页面启动一个已明确允许的测试任务，让手机应用进入后台或关闭页面并锁屏；确认通知标题显示对话名、正文显示“运行完成”。保持 Node 服务和任务运行。
4. 发起按当前审批策略需要确认或补充输入的测试任务，保持其等待状态；在锁屏通知出现后点击，核对返回正确的本机/SSH 主机和聊天。审批只能在登录后的实际页面完成。
5. 使用可控失败场景验证对话名和“运行失败”，并核对通知没有带出回复正文、命令或路径；分别关闭类别，确认该设备不再收到对应事件。
6. 让网页登录自然过期，核对仍有效授权的后台提醒；点击后重新登录并确认目标对话仍正确。随后明确退出，确认该登录关联设备不再收到通知，另一已授权设备仍独立可用。
7. 检查应用离线时的连接提示，确认没有缓存私人 API 响应或离线提交。网络恢复后核对真实聊天状态。
8. 发布一个新的构建，确认出现更新提示、执行任务期间不能更新、空闲时可主动更新；常规重建保留 `webdata` 后，再验证原设备订阅。服务重启和系统强退场景单独记录，不据此承诺活动任务或即时通知必定恢复。

若测试失败，先核对 HTTPS/Origin、通知许可和订阅状态，再检查服务是否存活、类别/授权期限、持久化卷及推送服务网络可达性。不要把日志中的设备 endpoint、密钥或登录数据公开到 issue。
