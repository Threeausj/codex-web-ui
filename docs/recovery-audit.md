# 连接恢复与执行核对审查（2026-10-08）

本轮继续检查大对话、多端回退、原生协议输入及自动化恢复。以下三个问题均有复现或旧实现对照，并已修复。测试只读历史或使用隔离 fixtures，不向真实会话提交模型任务。

## 已修复的问题

| 优先级 | 问题与影响 | 修复与证据 |
| --- | --- | --- |
| 高 | 断线期间另一端编辑回退会话，事件重放先于连接成功状态。页面清空旧历史后立即请求读取失败，随后轻量恢复可能把空白视图认定为可发送 | 回退使旧读取失效、取消发送就绪状态；断线时等恢复后重新确认历史。新增浏览器失败注入：两个回退通知先于连接状态、延迟历史响应，确认读取前禁止发送、恢复保留草稿并只显示保留的历史。旧实现该用例失败 |
| 高 | JSONL 输入每收到一块就计算整段字符串字节数、搜索换行，并不断拼接。大响应的累计扫描量随分块数增长，会阻塞所有共享该 Node 服务的连接；单批次包含多帧时还把整批大小误当单帧限制 | 使用字节片段累计每帧，搜索只遍历新收到的块，完整帧才合并与解码。保留每帧 64 MiB 上限；覆盖跨块中文／emoji、CRLF、16 MiB 历史及后续事件顺序、多帧批次、超限和连接停止后的处理 |
| 中 | 自动化使用分页模式创建原生会话，但执行核对依赖 `thread/read(includeTurns: true)` 的内嵌历史；丢失提交回执时也未识别原生 `userMessage.clientId` | 改为只读元数据及 `thread/turns/list`，优先匹配原 turn ID，缺失时匹配用户消息的客户端 ID；校验分页游标并设置页数／时间上限。分页确认完成记录可恢复，重复游标或找不到回执仍保留待核对，不能自动重试或重复提交 |

## 解析性能对照

隔离进程使用同一份 16,777,246 字节的 JSON 响应，分别模拟旧、新解析器，包含 `JSON.parse`；每项执行三次，记录中位数。测试在本机执行，期间同时运行浏览器回归，数据不包含真实消息。

可运行 `npx tsx scripts/json-lines-benchmark.ts` 重现对照。它只生成固定测试数据，不连接后台，也不属于自动测试的时间断言。

| 每块大小 | 旧解析耗时 | 新解析耗时 | 旧实现累计字节计数扫描量 | 新实现收到的字节数 |
| --- | ---: | ---: | ---: | ---: |
| 4 KiB | 31,424 ms | 44 ms | 34,384,904,222 | 16,777,246 |
| 32 KiB | 4,271 ms | 41 ms | 4,320,133,150 | 16,777,246 |

这些数字只说明 JSONL 收集与解析阶段，不能推导公网、SSH、浏览器渲染或首次打开会话的总时间。原生分页响应超过单帧 64 MiB 时仍会明确拒绝；首次加载仍需要接收历史，完整事件补齐后的恢复才可跳过读取。

## 仍需改进

聊天草稿的私有作用域统一、主机／项目跨文件事务、开发预览 WS 的发送积压保护和前端主入口拆分仍是后续建议。这些没有因为本轮连接修复而自动解决，详见 [项目审查](project-audit.md)。

自动化核对最多读取 100 页，分页部分最多等待 45 秒；超出范围时保留待核对，用户可打开原生执行会话查看。这是避免无界扫描与重复执行的边界。
